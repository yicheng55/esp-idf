## 什麼是 802.1AS (gPTP)

### 簡介

**IEEE 802.1AS** 是針對 **時間敏感網路 (Time-Sensitive Networking, TSN)** 設計的精準時間協議 profile。也稱為 **gPTP (generalized Precision Time Protocol)**。

### 主要特點

- 🎯 **專為工業自動化設計**: 滿足確定性網路需求
- ⚡ **更快的同步速率**: Sync 間隔 125ms (相比 802.3 的 1秒)
- 🔒 **強制 P2P 延遲機制**: 提供更準確的路徑延遲測量
- 📡 **專用 MAC 地址**: `01:80:C2:00:00:0E` (與橋接協議共用的預留範圍)
- 🏷️ **專用識別碼**: transportSpecific = 0x1

### 適用場景

✅ **適合使用 802.1AS**:
- 工業自動化與控制系統
- 時間敏感網路 (TSN) 環境
- 需要快速同步收斂的應用
- 所有網路設備都支援 gPTP

❌ **不適合使用 802.1AS**:
- 混合廠商設備，不確定 gPTP 支援度
- 需要與舊版 PTPv2 設備互通
- 網路流量敏感的應用（gPTP 流量較大）

## 與 802.3 的差異

### 技術參數對比

> 數據來源：`middlewares/3rd_party/ptpd-2.0.0/src/constants.h`（`DEFAULT_*` 與 `DEFAULT_*_8021AS` 巨集）。
> 若以 `-D` 編譯期覆寫或手動修改，請以實際編譯結果為準。

| 項目 | IEEE 802.3 (1588) | IEEE 802.1AS (gPTP) |
|-----|-------------------|---------------------|
| **標準** | IEEE 1588-2008 | IEEE 802.1AS-2011 / 2020 |
| **`transportType`** | `3` | `4` |
| **目的 MAC** | `01:1B:19:00:00:00` | `01:80:C2:00:00:0E` |
| **EtherType** | `0x88F7` | `0x88F7` |
| **`transportSpecific` / `majorSdoId`** | `0x0` | `0x1` |
| **`twoStepFlag`** | `FALSE`（可調） | **`TRUE`**（gPTP 強制 two-step） |
| **`delayMechanism`** | `E2E` 或 `P2P` | **強制 `P2P`**（由 `ptpd.c` 覆寫） |
| **Announce Interval** | `log2=1` → **2 s** | `log2=0` → **1 s** |
| **Sync Interval** | `log2=0` → **1 s** | `log2=-3` → **125 ms** |
| **PDelay Req Interval** | `log2=1` → **2 s** | `log2=-2` → **250 ms** |
| **Announce Receipt Timeout** | `6`（= 6 × Announce Interval） | `3`（= 3 × Announce Interval） |
| **網路流量** | 較低 | 較高（約 8 × Sync 頻率） |
| **兼容性** | 廣泛 | 需要明確支援 |

### 封包結構差異

#### PTP Header 第一個 Byte (messageType + transportSpecific)

```
802.3 模式:
  Bits 7-4: transportSpecific = 0x0
  Bits 3-0: messageType (0=Sync, 1=Delay_Req, etc.)

802.1AS 模式:
  Bits 7-4: transportSpecific = 0x1  ← gPTP 識別
  Bits 3-0: messageType
```

#### Ethernet Header 目的地址

```
802.3:   01:1B:19:00:00:00 (PTPv2 標準 multicast)
802.1AS: 01:80:C2:00:00:0E (IEEE 802.1 預留範圍)
```

## 前置條件檢查

### 1. 確認 Master 設備支援

#### 方法 A: 查看設備規格
- 檢查設備文件是否明確標示支援 IEEE 802.1AS
- 查看是否提到 "gPTP" 或 "Time-Sensitive Networking"

#### 方法 B: 使用 Wireshark 抓包分析

**步驟**:
1. 連接分析電腦到 PTP 網路
2. 啟動 Wireshark，選擇正確的網路介面
3. 應用過濾器: `ether proto 0x88f7`
4. 觀察 Master 發送的 PTP 封包

**分析重點**:

```
檢查 Ethernet Header:
  目的 MAC = 01:80:C2:00:00:0E  ← 支援 gPTP ✅
  目的 MAC = 01:1B:19:00:00:00  ← 僅支援 802.3 ⚠️

檢查 PTP Header (第一個 byte 的高 4 bits):
  transportSpecific = 0x1  ← gPTP ✅
  transportSpecific = 0x0  ← 標準 PTPv2 ⚠️
```

### 2. 檢查網路環境

- ✅ 所有交換器支援 IEEE 802.1AS (若有中間設備)
- ✅ 網路支援 Multicast (MAC: 01:80:C2:00:00:0E)
- ✅ 沒有 MAC 地址過濾阻擋 gPTP 封包
- ✅ 網路頻寬足夠處理更高的訊息頻率

## 驗證方法

### 階段 1: 啟動驗證

#### 檢查點 1.1: PTP 初始化

**預期輸出**:
```
PTPd_Init: transportType=4 (1=UDP/IPv4, 3=802.3, 4=802.1AS)
```

✅ **通過**: transportType = 4  
❌ **失敗**: 如果是 3 或 1，表示配置未生效，需重新編譯

#### 檢查點 1.2: 網路層初始化

**預期輸出**:
```
netInitL2: registered L2 RX callback, transport=4
```

✅ **通過**: transport = 4  
❌ **失敗**: 檢查 constants.h 和編譯設定

### 階段 2: 連接驗證

#### 檢查點 2.1: 接收 Announce 訊息

**預期輸出**（約每 1 秒，`DEFAULT_ANNOUNCE_INTERVAL_8021AS = 0`）:
```
handleAnnounce: received
handleAnnounce: from another foreign master
addForeign: New foreign Master added
```

✅ **通過**: 成功接收 Master 的 Announce  
❌ **失敗**: 
- Master 可能不支援 gPTP
- 網路連接問題
- MAC 地址過濾問題

#### 檢查點 2.2: 狀態轉換

**預期輸出**:
```
state PTP_LISTENING
→ state PTP_UNCALIBRATED
→ state PTP_SLAVE
```

✅ **通過**: 進入 SLAVE 狀態  
❌ **失敗**: 停在 LISTENING，表示無法建立同步

### 階段 3: 同步驗證

#### 檢查點 3.1: 接收 Sync/Follow-Up

**預期輸出**（約每 125 ms，`DEFAULT_SYNC_INTERVAL_8021AS = -3`）:
```
handleSync: received
handleFollowup: received
updateOffset
updateClock
```

✅ **通過**: 正常接收高頻訊息
⚠️ **注意**: 如果間隔是 1 秒，表示 Master 實際以 `log2=0` 送 Sync（通常代表對端非 gPTP 設定）

#### 檢查點 3.2: 時鐘收斂

**預期輸出**:
```
初始:
updateClock: offset from master: 0 s -2631160 ns, drift: -164447 ns

收斂中:
updateClock: offset from master: 0 s  -383920 ns, drift: -313442 ns

穩定:
updateClock: offset from master: 0 s      222 ns, drift:   1536 ns
```

✅ **通過**: offset 逐漸收斂至 <1µs  
❌ **失敗**: offset 持續震盪或發散

### 階段 4: Wireshark 驗證

#### 檢查本節點（不論 Master / Slave）發送的封包

> **重要**：gPTP 的 PDelay 是**按每條鏈路分別量測**，與角色無關。
> 不論本節點目前為 `PTP_MASTER` 或 `PTP_SLAVE`，皆會週期性送出 PDelayReq（見 `gptp_peer_delay_master.md` §2.2、§5.1）。

**過濾器**：`ether src [本節點 MAC] and ether proto 0x88f7`

**檢查項目**：
- ✅ 目的 MAC = `01:80:C2:00:00:0E`
- ✅ PDelayReq 間隔約 **250 ms**（`DEFAULT_PDELAYREQ_INTERVAL_8021AS = -2`）
- ✅ PTP Header[0] 高 4 bits（`majorSdoId` / `transportSpecific`）= `0x1`

#### 檢查對端 Master 發送的封包

**過濾器**：`ether dst 01:80:c2:00:00:0e and ether proto 0x88f7`

**檢查項目**：
- ✅ Sync 間隔約 **125 ms**
- ✅ Announce 間隔約 **1 秒**
- ✅ FollowUp 緊跟每筆 Sync（two-step）
- ✅ PDelayResp 正常回應本節點送出的 PDelayReq

## 故障排除

### 問題 1: 編譯後仍顯示 transportType=3

**症狀**: 啟動訊息顯示 `transportType=3` 而非 4

**原因**: 舊的編譯產物未清除

**解決**:
```
1. Keil MDK: Project → Clean Targets
2. 手動刪除 mdk_v5/Objects/ 目錄
3. Project → Rebuild all target files
4. 重新燒錄
```

### 問題 2: 停在 PTP_LISTENING 狀態

**症狀**: 
```
state PTP_LISTENING
(無法進入 UNCALIBRATED/SLAVE)
```

**可能原因**:
1. Master 不支援 gPTP
2. 網路未連接
3. Master 過濾了 gPTP MAC 地址

**診斷步驟**:

#### A. 檢查網路
```
確認 UART 輸出:
  Link: State changed from UNKNOWN to UP  ← 必須 UP
  DHCP: Assigned IP: 192.168.x.x          ← 必須有 IP
```

#### B. 使用 Wireshark 確認 Master 封包
```
過濾器: ether proto 0x88f7
查看: Master 發送的目的 MAC 地址

如果是 01:1B:19:00:00:00 → Master 使用 802.3 模式
→ 解決: 改回 TRANSPORT_IEEE_802_3
```

#### C. 檢查 Master 配置
- 確認 Master 啟用了 gPTP 模式
- 檢查 Master 的 domain number 是否匹配

### 問題 3: Master 不回應 PDelay Request

**症狀**:
```
issuePDelayReq
(但沒有收到 PDelayResp)
```

**原因**: Master 無法識別 Slave 的 gPTP 封包

**解決**: 
- 確認 Master 真正支援雙向 gPTP 通訊
- 可能需要在 Master 端明確啟用 802.1AS 模式
- 考慮改回 802.3 模式以提高兼容性

### 問題 4: 時鐘無法收斂

**症狀**:
```
updateClock: offset 持續在大範圍震盪
或 drift 值異常大
```

**可能原因**:
1. Master 與 Slave 模式不匹配
2. 硬體時鐘問題
3. 網路延遲不穩定

**診斷**:

#### A. 確認模式匹配
```
Slave: transportType=4, MAC 01:80:C2:00:00:0E
Master: 應該也使用相同的參數
```

#### B. 檢查 DM9058 PTP 功能
```
確認 UART 輸出:
  dm9058_init_ptp: PTP timestamp registers configured
  (檢查 TX/RX timestamp offset 設定正確)
```

#### C. 網路環境檢查
- 移除中間交換器，直接連接測試
- 確認無網路風暴或過載

### 問題 5: 收到 "Check not a PTP packet" 訊息

**症狀**:
```
low_level_input_ (Check not a PTP packet) rx len 64 dumpdata 40
   0   01 80 c2 00 00 00 ...
```

**說明**: 這是**正常現象**，不是錯誤

**原因**: 
- MAC 地址 `01:80:C2:00:00:xx` 範圍包含多種協議
- `01:80:C2:00:00:00`: LLDP、STP 等橋接協議
- `01:80:C2:00:00:0E`: gPTP
- lwIP 正確過濾了非 PTP 的封包

**處理**: 無需處理，系統運作正常

## 效能調優

> 以下三組巨集皆位於 `middlewares/3rd_party/ptpd-2.0.0/src/constants.h`，
> 都可以用編譯期 `-D` 覆寫（不必動原始檔），例如 Keil Options → C/C++ → Define 加：
> `DEFAULT_SYNC_INTERVAL_8021AS=-4`。

### 1. 調整 Sync Interval

```c
// 目前預設: -3 (125 ms)
#define DEFAULT_SYNC_INTERVAL_8021AS  -3

// 更快 (62.5 ms):
#define DEFAULT_SYNC_INTERVAL_8021AS  -4

// 更慢 (250 ms):
#define DEFAULT_SYNC_INTERVAL_8021AS  -2
```

**取捨**：
- 更快 → 更高精度、更快收斂，但 CPU / IRQ / 網路負載增加
- 更慢 → 降低負載，但收斂速度變慢

### 2. 調整 PDelay Request Interval

```c
// 目前預設: -2 (250 ms)
#define DEFAULT_PDELAYREQ_INTERVAL_8021AS  -2

// 常見範圍: -5 (31.25 ms) ~ 0 (1 s)
```

### 3. 調整 Announce Receipt Timeout

```c
// 目前預設: 3（= 3 × Announce Interval = 3 s）
#define DEFAULT_ANNOUNCE_RECEIPT_TIMEOUT_8021AS  3

// 提高容錯性（Master 可以斷線更久才觸發自升為 Master）:
#define DEFAULT_ANNOUNCE_RECEIPT_TIMEOUT_8021AS  6
```

## 效能指標

### 預期同步精度

基於 802.1AS 的高頻更新：

| 階段 | 時間 | Offset | 收斂速度 |
|-----|------|--------|---------|
| 初始 | T+0s | ~2-3ms | - |
| 快速收斂 | T+10s | <100µs | 快 |
| 精細調整 | T+30s | <10µs | 中 |
| 穩定 | T+60s | <1µs | 慢 |

**對比 802.3**: 收斂速度約快 **2-3 倍**

### 網路流量

| 訊息類型 | 802.3 | 802.1AS | 增加倍數 |
|---------|-------|---------|---------|
| Sync      | 1 / s     (log2=0)  | 8 / s  (log2=-3) | 8× |
| FollowUp  | 1 / s（two-step 才有） | 8 / s  | 8× |
| Announce  | 0.5 / s   (log2=1)  | 1 / s  (log2=0)  | 2× |
| PDelayReq（雙向）| 0.5 / s × 2 端 ≈ 1 / s | 4 / s × 2 端 ≈ 8 / s | 8× |
| PDelayResp(+FU) | 對應回覆 | 對應回覆 | ≈ 8× |
| **總計（粗估）** | ~ 4 / s | ~ 40 / s | **~10×** |

**注意**：實際 PDelayReq 往返頻率 = `1 / pow2s(logMinPdelayReqInterval)`，gPTP 為 **1/0.25 s = 4 次/秒（每端）**；網路負載較 1588 預設高約一個量級。
